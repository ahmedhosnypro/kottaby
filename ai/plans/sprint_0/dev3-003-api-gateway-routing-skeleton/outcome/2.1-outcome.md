## Semantic decisions recorded

1. **Version chain semantics = task-def semantics** (`APP_VERSION ?? npm_package_version ?? "dev"`). The C1-phase2 dispatch paraphrased `resolveAppVersion` as "reads package.json synchronously w/ fallback '0.0.0'". REJECTED as a paraphrase drift because FOUR aligned in-repo sources pin the env chain: tasks.md 2.1 def (incl. its explicit TE tier text "each fallback arm of `version ?? npm_package_version ?? \"dev\"`"), plan.md §128/§250, Phase-0 outcome §#13, and the **committed** Phase-1 docblock on `HealthCheckReturnType.version` (`health-check.types.ts:38`). A sync fs read would also contradict "no filesystem I/O" purity posture and add a runtime FS dependency to a lib module. No caching module state: each call re-reads the env snapshot (cheap, pure, observable). Note kept visible here for review waves.
2. Empty-string `APP_VERSION` still WINS arm 1 (`??` nullish-only semantics — matches chain spec literally).
3. Timestamp freshness under bun's fast loop proven with `Bun.sleepSync(5)` monotonic tick (deterministic, zero deps) instead of wall-clock luck.
4. Service uses `export namespace HealthCheckService { export function getHealthStatus() }` — exact precedent match with `RecitationCatalogService` (pure public catalog reader), giving the `HealthCheckService.getHealthStatus()` call-shape Tasks 3.1/3.4 expect.
