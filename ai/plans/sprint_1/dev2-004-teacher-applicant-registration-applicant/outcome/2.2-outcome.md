## ValidationError custom-code choice — corrupt stored status

**Choice: `new ValidationError("APPLICANT_STATUS_CORRUPT", t.errorsTranslations.applicantStatusCorrupt)`** — custom-code two-arg form, NOT the bare-message form.

Rationale (studied sources):

1. `docs/graphql/domain-error-extensions-code.md` Rule 4 mandates the `(code, message)` overload "when the error needs a specific code" and Rule 2 requires SCREAMING_SNAKE_CASE. A bare `ValidationError(msg)` would collapse every corruption reject into the generic `VALIDATION` bucket — un-distinguishable from client-input validation errors that upstream masking/metrics treat differently.
2. The doc's own precedent set (`RECURRING_CLASS_DAYS_REQUIRED`, `INVALID_DURATION`, `ROLE_FORBIDDEN`) is exact-file copy of this call shape.
3. The i18n layer keyed its transport copy as `errors.applicantStatusCorrupt`, and the ErrorsLabels header documents "keys are lowercase camelCase of the SCREAMING_SNAKE_CASE codes" — choosing `APPLICANT_STATUS_CORRUPT` keeps the machine code ↔ translation key bijective (`APPLICANT_NOT_FOUND ↔ applicantNotFound`, `APPLICANT_COOLDOWN_ACTIVE ↔ applicantCooldownActive`, `APPLICANT_STATUS_CORRUPT ↔ applicantStatusCorrupt`), matching how existing `NotFoundError("APPLICANT")` maps onto `applicantNotFound`.
4. Fail-closed intent (REQ-012/REQ-075): a data-integrity violation deserves its own telemetry dimension rather than blending into ordinary validation noise.

The cooldown reject similarly uses the already-recorded Task 1.3 producer mapping `ValidationError("APPLICANT_COOLDOWN_ACTIVE", …)`; missing rows use `NotFoundError("APPLICANT", …)` auto-generating `APPLICANT_NOT_FOUND`.

## ICU `{cooldownUntil}` interpolation approach (1.3 CF-1 compliance)

No runtime ICU expander exists in-repo (Task 1.3 CF-1) and no shared date util exists yet (0.2 finding #19 — Task 4.2 owns the FRONTEND one). Implemented server-side:

- Translated template read from `getServerTranslations(locale).errorsTranslations.applicantCooldownActive`.
- Simple typed expansion: `template.replace("{cooldownUntil}", formattedStamp)` — safe because the locale parity suites mechanically pin EXACTLY ONE placeholder named `cooldownUntil` in BOTH locales.
- **Formatter**: module-level immutable table of two `Intl.DateTimeFormat` instances (`ar`, `en`) with fixed options `{ timeZone: "UTC", year: "numeric", month: "2-digit", day: "2-digit", hour: "2-digit", minute: "2-digit", hour12: false }`.
- **Documented choices**: (a) fixed `timeZone: "UTC"` — byte-deterministic across environments, keeps tests flake-free (host TZ cannot drift into assertions); documented in service JSDoc; (b) `hour12: false` — removes am/pm-vs-ص variation risk inside substrings; (c) locale tag resolution mirrors `shared/locale/server.ts` exactly (only exact `"en"` selects English; everything else → `"ar"` = defaultLocale), so an interpolated stamp always lands in the language of the surrounding message even for out-of-domain locale strings.
- Replacement NOT done via regex capture groups or split/join tricks — single literal-token `replace` (first occurrence only; parity pin guarantees there is exactly one).
