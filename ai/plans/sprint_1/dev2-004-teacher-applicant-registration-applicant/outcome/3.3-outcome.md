## authScopes decision (CRITICAL — REQ-031 evidence)

- `{ role: [UserRole.Teacher] }` ALONE is WRONG here: with `ctx.role` null (anonymous), the role scope RETURNS false and `scopeAuthOptions.unauthorizedError` (builder.ts:99-107) maps scope-return failures onto the localized `ForbiddenError` → anonymous callers would get FORBIDDEN (403) instead of UNAUTHORIZED (401).
- A plain `{ authenticated: true, role: [...] }` map is ALSO wrong: Pothos scope-auth combines multiple keys of one scope map with **ANY** semantics by default — any authenticated caller would satisfy the first passing scope and non-teachers would be GRANTED. (builder.ts:39-42's "AND-composition" comment describes intent; the plugin's actual default strategy is any.)
- **Shipped form: `authScopes: { $all: { authenticated: true, role: [UserRole.Teacher] } }`** — explicit conjunction. Anonymous → the `authenticated` scope's thrown `UnauthorizedError` passes through the unauthorizedError mapping VERBATIM → `UNAUTHORIZED` (401). Authenticated non-teacher → role scope false → canonical localized `ForbiddenError` → `FORBIDDEN` (403). Both pinned by the integration suite (8/8 pass).
- ctx identity: `ctx.user.id` (verified against gqlContextFactory — `ctx.user: RegistrationReturnType | null`, `id: number`). A TS-narrowing guard (`if (!ctx.user) throw new UnauthorizedError(...)`) exists purely for type-narrowing (repo-wide no-non-null-assertion rule); unreachable in practice (scope guarantees the user), mirrors builder.ts's own message verbatim.
