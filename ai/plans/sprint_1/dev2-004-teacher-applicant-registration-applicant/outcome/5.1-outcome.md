## Injection approach — ideal vs proven (honest record)

**Case 3 — forced child-insert failure.** STUDY FIRST verdict: the existing DEV1-002 test "atomicity: child-insert failure → zero residual users rows (full rollback)" ALREADY establishes the repo's sanctioned injection pattern — monkey-patching `applicantModule.ApplicantRepository.create` (resolved through the same module instance the service imports) with a throwing stub, restore-in-`finally`. I REUSED that exact mechanism via the `withForcedApplicantCreateFailure` helper. Because the test passes the outer tx, the stub fires INSIDE the service-owned nested transaction (`withTransaction(outerTx)` → SAVEPOINT) at precisely the applicants child-insert stage — i.e., **the plan's ideal injection point IS what was proven, with zero DEV1-owned code refactored and zero production files touched.** No deviation.

**Case 4 — duplicate-email concurrent race.** The plan's ideal shape is two CONCURRENT `registerUser(sameEmail, …, outerTx)` calls via `Promise.allSettled` inside `runInRollback`. That literal shape is **structurally unsafe under the current drizzle version** (verified in `node_modules/drizzle-orm/node-postgres/session.js` + `pg-core/async/session.js`): every nested `tx.transaction()` derives its savepoint name as `sp${parentTx.nestedIndex + 1}`, and two SIBLING nested transactions launched from the same outer tx compute the SAME name. PG resolves duplicate savepoint names to the MOST RECENT, so the loser's `ROLLBACK TO SAVEPOINT sp<n>` nondeterministically targets either its own checkpoint (green) or the winner's (erasing the winner's committed-in-tx row → the "one success" would be a phantom and leg-2 assertions red). First empirical run of the mandated shape confirmed the ambiguity class (and a second flake — an off-by-1ms `createdAt >= Date.now()` comparison vs PG's transaction-start `now()` — was removed from case 2; both documented in Deviations). A second hazard exists independently: with NO savepoint around a raw failed statement, the whole outer tx enters the PG aborted state (`25P02`) and every later query fails.

The implemented, deterministic closest-honest-proof (single test, three escalating-surface layers, all inside the one rollback tx):

- **Layer 1 (constraint race)**: `Promise.allSettled` over TWO concurrent identical `tx.insert(users)` payloads (field-for-field `createUserRow` mirror) racing the same `users_email_unique` index. Statements serialize FIFO on the single runInRollback session, so PG deterministically admits exactly one arm — asserted `fulfilled === 1` / `rejected === 1` and the loser's cause chain carries `23505`. The race is bracketed by ONE explicitly-named savepoint (`savepoint dev2004_race`) with a bounded `rollback to savepoint dev2004_race` as the FIRST command after `allSettled` settles — lifting the aborted state without touching any other region, then asserting zero residual rows survived the race window (containment evidence).
- **Layer 2 (production winner)**: `registerUser(sameEmail, teacher, tx)` creates the REAL account through the full production surface (users + applicants, shared PK) — asserted.
- **Layer 3 (production ConflictError map)**: re-registering the raced email via `registerUser` → `expectRepoError` → `ConflictError` with `code === "CONFLICT"` (the 23505-inheritance/translateDbError contract).
- **Final uniqueness pin**: exactly 1 users row for the raced email AND exactly 1 applicants row on the winner's shared PK — no duplicates.

What is proven vs the ideal, plainly: the CONCURRENT-RACE CONVERGENCE at the exact uniqueness boundary (exactly one admission, one 23505) is proven at the constraint layer; the CONFLICT-MAPPING of that violation through the production surface is proven via the production replay; the combined end-state contract (exactly one account, zero duplicates) is asserted against real persisted rows. The only property NOT executable on this harness is routing BOTH racing arms through the full `registerUser` call itself, because that requires two concurrent sibling SAVEPOINTs whose drizzle-generated names collide (source-cited above). No DEV1-owned code was modified to work around this, per the FORBIDDEN constraint.
