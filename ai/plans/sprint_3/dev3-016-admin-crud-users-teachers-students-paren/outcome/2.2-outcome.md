## Carry-Forward Knowledge for Task 2.4 (`AdminUserManagementService`)

(Same as Task 2.1's carry-forward, with these Journey B/C-specific additions:)

1. **createUser for `role=teacher`**: produces `users` + `applicants` rows ONLY (NEVER a `teacher` row). The `applicants` row is created via `ApplicantRepository.create(userId, tx)` with the canonical pending state (`status="pending"`, `verificationAttempts=0`, `lastAttemptAt=null`, `cooldownUntil=null`). The journey asserts `countTeacherRowsForUser(newApplicant.id) === 0` (the certification lock).

2. **getUserDetail applicant projection**: returns `AdminUserDetailReturnType` with `applicant: ApplicantProfileReturnType | null` populated (non-null) for a teacher-role user with an `applicants` row; `teacher: AdminTeacherSnapshotReturnType | null` is `null` until the verification loop (DEV3-018 / DEV1-005) creates a `teacher` row. The journey asserts `detail.teacher === null` for the new applicant.

3. **updateUser whitelist**: `AdminUpdateUserPatchInput = { fullName?, phone?, country?, gender?, dateOfBirth? }`. Field-by-field mapping into `AdminUserUpdateDbPatch` (NO `{ ...input }` spread). The journey's Journey B step 4 patches `fullName` only and asserts the `applicants` row is byte-identical to pre-call (cross-entity purity — the `users` UPDATE touches only `users.full_name` / `users.updated_at`, never the `applicants` row).

4. **Audit row for updateUser**: `details` JSON contains `{"changedFields":["fullName"]}` — field NAMES only, never values (sensitive-field discipline). The journey doesn't assert the `details` JSON shape directly (the implementer should ensure the JSON is PII-minimal); the journey asserts the existence of exactly one `audit_logs(Update, actorId=admin, entityId=newApplicant.id)` row.

5. **Defense-in-depth authorization at the service layer** (CRITICAL — Task 2.4 implementer must extend the plan §4.1 contract to add `actorId` on EVERY method, not just mutations):
   - `listDirectory(filters, page, pageSize, locale, actorId, outerTx?)` — `actorId` added at position 5.
   - `getUserDetail(userId, locale, actorId, outerTx?)` — `actorId` added at position 3.
   - The journey's Journey C step 1 (anonymous) and step 2 (non-admin) pass `actorId` on EVERY service call (including reads) and expect typed denials (`UnauthorizedError` for anonymous; `ForbiddenError` for non-admin).
   - The journey's Journey B step 5 (new applicant calls `listDirectory` with `actorId = newApplicant.id`) expects `ForbiddenError` — defense-in-depth beyond the GraphQL authScope gate.

6. **ADMIN_ROLE_CREATION_FORBIDDEN**: the runtime role-pre-guard in `createUser` checks `input.role` against the `RegisterPublicRole` union (`student | teacher | parent` — `admin` is structurally excluded). The journey deliberately casts around the type via `as unknown as AdminCreateUserSubmitInput` to test the runtime guard. Task 2.4 must implement the guard to throw `ConflictError` with code `ADMIN_ROLE_CREATION_FORBIDDEN` (the existing `ConflictError` constructor hardcodes `code = "CONFLICT"` — Task 2.4 must extend it to accept a custom code).

7. **Cross-actor visibility table** (per plan §4.4): after Journey B step 1, the admin sees the applicant detail (pending, attempts=0, cooldown=NULL, NO `isApproved` artifact anywhere); the new applicant sees their own pending profile truthfully via `myApplicantProfile` (cross-ticket contract — the existing `ApplicantLifecycleService.getMyApplicantProfile` is consumed, NOT re-implemented).
