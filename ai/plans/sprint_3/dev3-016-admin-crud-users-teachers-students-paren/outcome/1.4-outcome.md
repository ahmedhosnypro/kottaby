## What Was Implemented

### 1. The `AdminUsersLabels` interface — `shared/locale/types/adminUsers/index.ts`

A new `AdminUsersLabels` interface with 15 sub-blocks covering the complete admin user-management UI chrome surface (directory + detail + dialogs + snackbars + pagination). The interface follows the **nested sub-block** pattern (matching the `errors.adminUsers` precedent from Task 1.3) rather than the flat-with-prefix pattern (used by `ApplicantLabels` / `DashboardLabels`), because the task spec uses dotted names for the bulk of the keys (`createDialog.title`, `deleteConfirm.consequences`, `detail.profile`, `pagination.page`, etc.) and several leaf-name pairs would otherwise collide (`role` is both a table header AND a filter label; `country` is both a table header AND a filter label; `deleted` is both a status badge AND a snackbar). Nesting eliminates the collisions cleanly.

Sub-blocks:

| Sub-block | Leaves | Purpose |
|---|---|---|
| top-level | `title`, `detailTitle` | Page header band headings |
| `headers` | `name`, `email`, `role`, `country`, `status`, `lastActive`, `createdAt`, `actions` | Directory table column headers |
| `statusBadges` | `active`, `suspended`, `blocked`, `deleted` | Governance status chip labels |
| `roleLabels` | `admin`, `teacher`, `student`, `parent` | Role chip labels (admin = super-admin) |
| `filters` | `role`, `governance`, `country`, `search`, `searchPlaceholder` | Filter-bar control labels + search input placeholder |
| `emptyState` | `title`, `message`, `cta` | Empty-state copy inside the table body |
| `errorState` | `title`, `message`, `retry` | Error-state copy when the directory query fails |
| `createDialog` | `title`, `fullName`, `email`, `phone`, `password`, `gender`, `country`, `role`, `submit`, `cancel` | Create-user dialog field labels + actions |
| `editDialog` | `title`, `fullName`, `phone`, `country`, `gender`, `dateOfBirth`, `submit`, `cancel` | Edit-user dialog field labels + actions (no `email`/`role`/`password` — REQ-016 whitelist) |
| `deleteConfirm` | `title`, `message`, `consequences`, `confirm`, `cancel` | Soft-delete confirm dialog copy + consequences line |
| `reactivateConfirm` | `title`, `message`, `confirm`, `cancel` | Reactivate confirm dialog copy |
| `detail` | `profile`, `governance`, `applicant`, `teacher`, `student`, `parent`, `backToDirectory`, `notFoundTitle`, `notFoundMessage` | Detail page section headings + back affordance + not-found copy |
| `selfDeactivationAlert` | `title`, `message` | Self-deactivation guard alert rendered inside delete-confirm dialog |
| `snackbars` | `created`, `updated`, `deleted`, `reactivated` | Mutation-success snackbar copy |
| `pagination` | `page`, `of`, `total`, `next`, `previous`, `pageSize` | Pagination control labels + counters |

Total: 2 top-level leaves + 8 + 4 + 4 + 5 + 3 + 3 + 10 + 8 + 5 + 4 + 9 + 2 + 4 + 6 = **75 leaf strings** across 15 grouped sub-blocks. All leaves are plain strings — no ICU placeholders (admin-authored DATA is composed verbatim into row copy inside the component, never interpolated into a localized template).

## The `Translation.AdminUsers` enum member — important reconciliation

The task spec mentions adding a `Translation.AdminUsers = "adminUsers"` enum member and notes it is "CRITICAL for Task 4.2/4.3 which uses `useAppTranslation(Translation.AdminUsers)`".

**Reconciliation:** There is **no `Translation` enum anywhere in the codebase** — confirmed by `grep -rn "enum Translation" shared/ frontend/ backend/` returning zero hits. The plan/spec language `useAppTranslation(Translation.<Namespace>)` is the plan's **shorthand** for the codebase's actual i18n access pattern: a **`NamespaceHandle` const** consumed as `useAppTranslation(<Handle>)`. This was explicitly resolved by the DEV2-004 plan-review-R1 ruling DISP-4 (BINDING): *"Global i18n lens: namespace handles (`useAppTranslation(Applicant)`, handles from `@/shared/locale`), one-arg `getServerTranslations(locale)` bundle access, `ctx.t("errorsTranslations"|"applicantTranslations")`; NO Translation enum ever created; all `Translation.<Ns>` mentions read accordingly"* (see `ai/plans/sprint_1/dev2-004-teacher-applicant-registration-applicant/plan-review-R1.md` line 208 + `outcome/0.3-outcome.md` line 20).

The artifact that fulfills the plan's "Translation.AdminUsers enum member" requirement is therefore the **`AdminUsers` const namespace handle** exported from `shared/locale/namespaces/adminUsers/adminUsers.namespace.ts` (and re-exported via `shared/locale/namespaces/adminUsers/index.ts` + the top-level `shared/locale/namespaces/index.ts`). Task 4.2/4.3 client components will consume it as:

```ts
import { AdminUsers } from "@/shared/locale/namespaces/adminUsers";
// or equivalently:
import { AdminUsers } from "@/shared/locale/namespaces";

const t = useAppTranslation(AdminUsers);  // resolves to AdminUsersLabels
// then: t.headers.name, t.statusBadges.active, t.createDialog.title, t.deleteConfirm.consequences, ...
```

The server-side equivalent (for any SSR shell component) is:

```ts
import { getTranslations } from "@/shared/locale/server";
const t = getTranslations(locale).adminUsersTranslations;  // AdminUsersLabels
```

This is the canonical consumer shape — property access only, never `t('key')` calls.
