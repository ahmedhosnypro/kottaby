## 1. Executive Summary & Problem Statement

- **Feature:** An admin-only, single-query platform analytics dashboard (FR-10.6 / Workflow 05 "Platform Analytics"): one server-side snapshot composed of user counters, session lifecycle counters, revenue aggregates, subscription state distribution, teacher presence, rating aggregates, operational health indicators, and 30-day daily trends — rendered as a dashboard page with stat cards, breakdown sections, and a trend chart.
- **Problem from user perspective:**
  - **Super Admin** needs one truthful "state of the platform" surface — today the only aggregate read is `adminUserStats` (user counters only, `backend/graphql/query/admin/admin-users.query.ts:102-118`). Sessions, money, subscriptions, and teacher presence have NO aggregate read at all; answering "how many sessions this week" or "revenue this month" requires hand-written SQL.
  - **Operations review / audit readers** (DEV3-020 adjacency) get a page whose numbers they can trust because every figure is computed from set-oriented SQL against the real tables, never cached and never client-assembled.
  - **Other roles** (teacher, student, parent) must never see platform-wide aggregates — the surface is BFLA-gated at three layers.
- **Business value:** FR-10.6 is an M3 "Parent Portal & Admin Governance" scope item (`docs/planning/ROADMAP.md` §M3) and a `docs/planning/PRODUCTION_READINESS.md` launch-adjacent capability (platform health/oversight). It is also the rendering substrate later analytics tickets (drill-down pages, CSV export, cached/alerted metrics) build on — those are explicitly OUT of scope here.
- **Actors involved:**
  - **Admin (caller/observer):** the ONLY authorized reader.
  - **Student / Teacher / Parent (data subjects & denial probes):** their payments, subscriptions, sessions, and ratings are the OBSERVED substrate; as callers they MUST be denied (403 at the scope layer, 403 at the service layer, byte-identical zero side effects).
  - **Governed admin (suspended/blocked/deleted holding a live token):** MUST be denied at the SERVICE tier (request-time governance re-check — see REQ-032; the GraphQL context boundary is documented as NOT fail-closed for governed users).
  - **Downstream consumers:** DEV3-020 (audit browsing — unaffected; reads never audit), future drill-down/export tickets.
- **Non-goals (explicitly OUT of scope):**
  - NO writes, mutations, or invalidations of any kind (zero `notifications`, zero `audit_logs`, zero state mutation — read purity is a tested invariant).
  - NO drill-down detail pages, NO CSV/PDF export, NO date-range pickers, NO custom granularity arguments (windows are fixed by contract — REQ-012/015).
  - NO server-side caching of metrics (fresh read per request; client polls on a fixed interval) and NO realtime-push of metrics (the WS fan-out engine is untouched).
  - NO per-teacher / per-student / per-plan drill-down, NO financial auditing surfaces (wallets/withdrawals detail is DEV3-022b — this ticket surfaces only the two WHOLE-PLATFORM health counters), NO admin user-management edits (DEV3-016 surface untouched).
  - NO new enums, NO new tables/columns, NO prepared-statement surface obligations beyond the documented dynamic-query posture.
  - NO `escapeLikeWildcards` surface: there is ZERO user-authored search/filter text on this feature (verified constraint — the obligation does not arise).

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (Single Snapshot Query Surface):** WHEN an admin requests analytics THEN the system SHALL expose exactly ONE GraphQL query `adminPlatformAnalytics: PlatformAnalytics!` carrying ZERO arguments and returning the full snapshot in one round trip. There SHALL be NO second analytics query, NO filter/granularity/section arguments (closed input surface).
- **REQ-011 (Snapshot Composition & Capture):** WHEN the service executes THEN it SHALL capture exactly ONE `now: Date` per request, SHALL populate `generatedAt` from it, and SHALL derive every window boundary (today / ISO week / month / 24h / 7d / 30d) from that single captured instant — never re-sampling wall clock mid-request.
- **REQ-012 (Users Section):** WHEN the snapshot is composed THEN `users` SHALL carry the existing ten `AdminUserStatsReturnType` counters VERBATIM from `AdminUserRepository.getStats` (reuse, REQ-002) PLUS `recentlyActive24h` = count of non-governed users with `last_active_at > now − 24h` (the column's B.15 ownership purpose).
- **REQ-013 (Sessions Section):** WHEN the snapshot is composed THEN `sessions` SHALL carry: `total`, `today` (started-day window ≥ today 00:00 UTC), `thisWeek` (≥ ISO week start Monday 00:00 UTC), `thisMonth` (≥ month start 00:00 UTC), per-status counts `scheduled / started / completed / cancelled / disputed` (all five `SessionStatus` members present even when zero), and `awaitingConfirmation` = `status='completed' AND confirmed_by_student_at IS NULL`.
- **REQ-014 (Revenue Section — Money as Exact Strings, Never Floats):** WHEN revenue is computed THEN `gatewayRevenueByCurrency` SHALL group `student_payments` on `status='paid'` by `currency`, summing via SQL (`sum(amount)::text`-class exact aggregation) and exposing amounts as **decimal strings** (`totalAmount`, `last30DaysAmount`) — conversion through JS `number` for money is PROHIBITED (float drift). `paidPaymentsCount` SHALL accompany each currency bucket. Empty payment history SHALL yield an EMPTY array (never a phantom zero-currency row).
- **REQ-015 (Offline-Payment Honesty — B.9 / INV-PAY5):** WHEN the revenue section is composed THEN it SHALL ALSO carry `offlineActivationsCount` = count of `subscriptions` whose `payment_method ∈ {offline_cash, bank_transfer, scholarship}` — because offline direct-onboarding payments BYPASS `student_payments` (INV-PAY5). The canonical doc SHALL state verbatim that `gatewayRevenueByCurrency` excludes offline activations; mixing the two into one number is PROHIBITED.
- **REQ-016 (Subscriptions Section):** WHEN composed THEN `subscriptions` SHALL carry: `total`, plus per-status counts for all five `SubscriptionStatus` members (`active`, `pending`, `expired`, `cancelled`, `suspended`), PLUS `activeInWindowNow` reusing the ACTIVE-window semantics verbatim (`status='active' AND coalesce(start_date, now) <= now AND (end_date IS NULL OR now < end_date)` — the proven shape at `backend/db/repo/admin/admin-user.repository.ts:337-346`).
- **REQ-017 (Teacher Presence Section):** WHEN composed THEN `teachers` SHALL carry `certifiedCount` (`teacher.is_approved = true`), `evaluatorCount` (`is_evaluator = true`), and `onlineNowCount` (`is_approved = true AND is_online = true`) — applicants (no `teacher` row, per B.7) are structurally excluded.
- **REQ-018 (Ratings Section — Two Honest Families, Nullable When Empty):** WHEN composed THEN `ratings` SHALL carry `averageSessionRating` = mean of `reports.student_rating_by_teacher` (0–5 band, check-constrained at `backend/db/schema/classes/reports.ts:29,36-41`) with `sessionRatingsCount`, AND `averageEvaluationScore` = mean of `evaluations.score` (0–100 band, `backend/db/schema/teachers/evaluations.ts:32,43`) with `evaluationScoresCount`. WHEN a family has zero rows THEN its average SHALL be `null` (honest emptiness — never a fabricated 0). Averages SHALL round to exactly 2 decimal places server-side.
- **REQ-019 (Operational Health Indicators):** WHEN composed THEN `health` SHALL carry exactly: `pendingDisputes` (`session.status='disputed'` count) and `pendingWithdrawals` (`teacher_transaction` with `type='withdrawal' AND status='pending'` count). No other indicator may be silently added (the frozen SDL inventory is the contract).
- **REQ-020 (30-Day Daily Trends — Zero-Filled):** WHEN composed THEN `sessionTrendDaily` SHALL be 30 consecutive day buckets ending at `now`'s day (UTC), each `{ bucketStart, count }` of sessions created that day, and `revenueTrendDaily` SHALL be 30 buckets of `{ bucketStart, currency, amount }` for PAID `student_payments` grouped by day+currency. Both series SHALL be **zero-filled for missing days** server-side (the chart never receives gaps); currency buckets absent on a given day contribute nothing (sparse per-currency, zero-filled per-currency presence is assembled from the currency set).
- **REQ-021 (Freshness Contract — No Caching):** WHEN the query executes THEN it SHALL read the database on EVERY request (no server cache, no memoized module state) and SHALL return `generatedAt = now`. The UI freshens via polling (REQ-064). Shared mutable module state is PROHIBITED.
- **REQ-022 (Read Purity — Zero Side Effects):** WHEN ANY analytics read executes (success OR denial) THEN it SHALL write ZERO rows to ANY table, emit ZERO notifications, and append ZERO `audit_logs` rows (reads are not audited — Workflow 05 §7.2 audits MUTATIONS; JR-C-1 parity means denials also write nothing). The domain log SHALL receive NOTHING on happy-path reads (silent-success parity with `ApplicantLifecycleService.getMyApplicantProfile`, `backend/services/teachers/applicant-lifecycle.service.ts` logging posture).
- **REQ-023 (Currency Containment):** WHEN multiple currencies exist THEN no metric SHALL ever sum across currencies; cross-currency totals are structurally impossible (there is NO total field — only per-currency rows).
- **REQ-024 (Temporal Contract):** WHEN day/week/month boundaries are computed THEN they SHALL be UTC (`date_trunc` or equivalent UTC calendar math), documented as such in the canonical doc; `bucketStart` values SHALL be midnight-UTC instants exposed via the `DateTime` scalar.
- **REQ-025 (Performance Shape):** WHEN the repository SQL is authored THEN every metric SHALL be a set-oriented aggregate read (no per-row hydration, no N+1, no DataLoader need — the root field resolves the whole object in one service call); trend reads SHALL be bounded by the 30-day window; all reads SHALL run inside the request's single transaction.
- **REQ-026 (Deterministic Testability):** WHEN tests assert windowed counters THEN fixtures SHALL use timestamps RELATIVE to the service-captured `now` (never hardcoded absolute dates), and repository tests SHALL inject `now` where the repo method accepts it (repo methods take an explicit `now: Date` parameter — the service owns clock capture, repos stay pure).

### 2.3 Security, Authorization & Tenancy

- **REQ-030 (BFLA — Admin-Only, `$all` Conjunction):** WHEN the query is registered THEN `adminPlatformAnalytics` SHALL carry `authScopes: { $all: { authenticated: true, role: [UserRole.Admin] } }` (load-bearing conjunction — the ANY-semantics hazard documented at `docs/teachers/applicant-lifecycle.md` §3; pattern anchor `backend/graphql/query/admin/admin-users.query.ts:74-79`). Anonymous → `UNAUTHORIZED` (401 semantics); non-admin → `FORBIDDEN` (403) BEFORE the resolver runs. `PUBLIC_OPERATIONS` (`backend/lib/gateway/public-operations.ts:36-46`) MUST remain the frozen six — analytics is NOT public.
- **REQ-031 (Service-Layer Actor Re-Verification):** WHEN `PlatformAnalyticsService.getPlatformAnalytics(actorId, locale, outerTx?)` executes THEN it SHALL re-verify the actor via `UserRepository.findById(actorId)` (parity with `assertActorAdmin`, `backend/services/admin/user-management.service.ts:240-271`): `actorId ≤ 0` or row absent → `UnauthorizedError`; role ≠ admin → `ForbiddenError`. Both denials BEFORE any aggregate read and BEFORE any transaction opens, with ZERO writes.
- **REQ-032 (Governed-Admin Denial — Service-Tier Governance Re-Check):** IF the re-verified admin row is governed (`isDeleted` OR `isBlocked` OR `suspended`) THEN the service SHALL throw `ForbiddenError` with the EXISTING localized message (`accountDeleted` / `accountBlocked` / `accountSuspended`) in deterministic order deleted → blocked → suspended. RATIONALE (documented divergence from `assertActorAdmin`'s role-only check): `createGraphQLContext` (`backend/graphql/gqlContextFactory.ts:167-239`) applies NO governance filter at request time — a suspended admin holding a live token would otherwise read whole-platform aggregates. The divergence and its reason SHALL be recorded in the canonical doc.
- **REQ-033 (BOLA — Zero-Argument Surface):** WHEN the query is defined THEN it SHALL carry NO arguments of any kind — there is no `userId`, no date input, no section selector; no client can steer the read beyond the fixed contract. Aggregate anonymity holds by construction (no per-entity rows are ever exposed — only counts/sums/averages).
- **REQ-034 (BOPLA):** WHEN the surface ships THEN there SHALL be NO input type at all; nothing client-controlled reaches a Drizzle call. (A closed zero-argument query is the strongest mass-assignment posture — verified by wire probes that any argument dies as `GRAPHQL_VALIDATION_FAILED`.)
- **REQ-035 (Query Safety — No Wildcard Surface):** WHEN repository SQL is authored THEN it SHALL use parameterized equality/aggregate predicates ONLY; NO LIKE/ILIKE exists on this feature, so NO `escapeLikeWildcards` obligation arises (verified constraint — recorded so future drill-down tickets re-evaluate); NO inline `--` comments inside any `sql` template; NO string interpolation of any value into SQL text.
- **REQ-036 (Log Hygiene):** WHEN a denial fires THEN exactly ONE `logger.logDomainError` SHALL be emitted per denial with context bounded to `{ code, entity: "users", entityId, locale }` — never metric payloads, never SQL text. `console.*` is forbidden; backend logging comes from `@/backend/lib/logger`.
- **REQ-037 (Oracle Hygiene):** WHEN any denial surfaces THEN it SHALL disclose only canonical localized copy (`unauthorized` / `forbidden` / governance-held messages) — aggregate contents are never partially disclosed on a denial path (the query is all-or-nothing by construction).
- **REQ-038 (Rate-Limit Posture — Recorded, Not Built):** WHEN the query ships THEN it SHALL inherit the existing platform posture (fail-open stub); a bespoke analytics limiter is a deferred-ledger forward item owned by the rate-limiting hardening stream.

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (One Transaction Per Snapshot):** WHEN the service composes a snapshot THEN all repository reads SHALL execute inside ONE `withTransaction(outerTx, tx => { … })` execution, every repository call receiving that SAME `tx` (optional trailing `tx?: DBTransaction` on every new repo method so `runInRollback` suites can assert rollback cleanliness). Mixed `tx`/`db` access is PROHIBITED.
- **REQ-041 (Snapshot Consistency Semantics — Documented, Honestly):** WHEN the snapshot is read THEN statement-level visibility follows the default isolation (per-statement snapshots); cross-metric drift between two statements of the same request is ACCEPTED and documented (a monitoring dashboard is not a ledger). A `REPEATABLE READ` upgrade was considered and REJECTED (locks nothing, costs a longer-lived snapshot, solves no correctness requirement here).
- **REQ-042 (Zero Fixture Mutation):** WHEN any analytics read executes against a populated database THEN every observed table (`users`, `session`, `student_payments`, `subscriptions`, `teacher`, `evaluations`, `reports`, `teacher_transaction`) SHALL be byte-identical before and after — fixture-immutability tests SHALL prove this.
- **REQ-043 (No Schema Drift):** WHEN the ticket completes THEN `git diff` on `backend/db/schema/**` and `backend/db/migration/**` SHALL be EMPTY (reads only; existing indexes cover predicate columns — no new index is introduced by this ticket).
- **REQ-044 (Query Construction Rules):** WHEN aggregate SQL is authored THEN window/grouping queries MAY use parameterized `sql` fragments; NO prepared statements for these dynamic aggregate reads (`docs/drizzle/prepared-statements.md`); NO `inArray`+placeholder combination; every `now`-derived bound is a bound parameter, never inline-interpolated text.
- **REQ-045 (Concurrent Read Tolerance):** WHEN many admins poll concurrently THEN each request SHALL compose independently with no shared mutable module state; there are NO locks to order because nothing is written (a read-only surface needs no concurrency primitive — this is asserted, not assumed, by the concurrent-read journey).

### 2.9 Cross-Actor Workflow Scenarios (Journeys)

> The dashboard is ADMIN observation over state created by OTHER roles (students pay, teachers serve sessions, parents/subscriptions populate counters). Every journey maps 1:1 onto `test/workflows/admin/platform-analytics.journey.test.ts`.

**Actor Table:**

| Actor | Role | Can Do | Cannot Do |
|---|---|---|---|
| Admin (observer) | `admin` + governed=false | read the full snapshot; observe exact metrics | mutate anything from this surface |
| Governed admin | `admin` + `suspended`/`isBlocked`/`isDeleted` | nothing here | read the snapshot (`FORBIDDEN`, service tier) |
| Student (fixture + denial probe) | `student` | shape counters via its subscription/payment/session rows | call the query (`FORBIDDEN`) |
| Certified teacher (fixture + denial probe) | `teacher` + approved row | shape `teachers.onlineNowCount`, sessions, ratings | call the query (`FORBIDDEN`) |
| Parent (fixture + denial probe) | `parent` | contribute to user counters | call the query (`FORBIDDEN`) |
| Anonymous / `actorId=0` | — | nothing | read (`UNAUTHORIZED`) |

**Ordered Step Lists + Cross-Actor EARS (observer-perspective):**

- **Journey A — Cold platform honesty:** (1) System → committed cast = admin ONLY (plus whatever pre-existing rows the shared DB holds — baselined, never assumed) → (2) Admin reads → every journey-touched counter family reports `baseline + 0`, trend series are fully populated (zero-filled 30 buckets), both rating averages are `null` for families with no journey rows. WHEN an admin reads a platform with no journey fixtures THEN every journey-owned metric SHALL differ from its pre-suite baseline by exactly zero AND trend arrays SHALL still be fully populated.
- **Journey B — Full cast observation:** (1) System → commit: student + ACTIVE-window paid subscription + one paid EGP payment today + one paid USD payment today; certified teacher `is_online=true`; a second certified teacher offline; one session `completed` (confirmed) today; one session `completed` unconfirmed; one `disputed` session; one `scheduled` session; one `cancelled` session; one pending withdrawal; one report + one evaluation; a governed student (excluded from active counts) → (2) Admin reads → EVERY metric equals baseline + the exact fixture delta (`sessions.today=+4`, `awaitingConfirmation=+1`, `pendingDisputes=+1`, `pendingWithdrawals=+1`, `teachers.onlineNowCount=+1`, revenue shows TWO separate currency rows with the exact paid sums, `sessionTrendDaily` last bucket = +4). WHEN any actor family commits platform activity THEN the admin's NEXT read SHALL reflect it exactly — and WHEN a non-admin actor's own state changes THEN that actor remains structurally unable to read the aggregate (`FORBIDDEN` every time).
- **Journey C — Freshness evolution (anti-cache proof):** (1) Admin reads (t1) → (2) System commits one ADDITIONAL paid payment (today, EGP) + one additional completed session (today) → (3) Admin reads again (t2) → the deltas (+1 session, +EGP amount, EGP row ascends, `generatedAt` at t2 > t1) are visible with no staleness. WHEN two sequential admin reads bracket a new payment THEN the second read SHALL expose exactly the delta — cached answers are a correctness bug here.
- **Journey D — Denial & purity matrix:** (1) Anonymous actorId=0 → `UnauthorizedError`; (2) student/teacher/parent direct service calls → `ForbiddenError`; (3) suspended admin (live-credentials scenario simulated at the service tier) → `ForbiddenError`; (4) EVERY denial and BOTH happy reads in A–C leave EVERY table byte-identical, ZERO `audit_logs` rows, ZERO notifications — read purity is asserted by row-count+content probes, not assumed. WHEN any non-admin or governed-admin attempts the analytics read THEN every observing actor SHALL see zero state change AND the platform SHALL record zero audit/notification side effects for the attempt.
