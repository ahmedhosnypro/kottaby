## 2. set-locale adoption decisions (explicit, per R1 correction #4)

1. **POST = full envelope adoption.**
   - Success: `apiSuccessResponse({ locale }, { requestId })` → body exactly `{ data: { locale }, requestId }`, status taxonomy-free 200 (success statuses live outside REQ-010 by design).
   - requestId resolved ONCE via `resolveRequestId(request.headers)` (Decision D4); echoed on every POST/GET error envelope.
   - Error paths all through `apiErrorResponse(..., { locale, requestId })` with statuses derived EXCLUSIVELY from the REQ-010 taxonomy map — zero numeric error-status literals remain in the file:
     - cross-origin/non-allowed origin → `ForbiddenError(localized invalidOrigin)` → `FORBIDDEN`/403 (gating logic itself unchanged);
     - malformed JSON body → syntax-fault gate returns `BAD_REQUEST` carrier localized with the canonical `badRequest` key (transport-class client fault, mirroring the REQ-016 preflight posture of the graphql route); a NON-syntax read fault rethrows into the single masked hop;
     - invalid locale (POST body or GET query) → `BAD_REQUEST` carrier localized with `invalidLocale`;
     - everything else (unknown throw) → Hop-C masking: 500 `INTERNAL_SERVER_ERROR`, localized generic message, zero-leak body, exactly ONE correlated redacted `logger.error` whose bag carries the SAME `requestId` (REQ-012/013 parity proven in-test).
2. **GET = partial adoption (documented success-body exemption).** The full-navigation switch is, by product contract, a cookie-carrying redirect (`Set-Cookie NEXT_LOCALE` + `Location`) so the browser lands on the next document with the cookie applied (`useLanguageSwitch` uses `window.location.replace`). A JSON envelope cannot coexist with navigation semantics ⇒ same exemption class reserved for future provider-ack webhooks. GET **error** branches ARE enveloped (400 w/ requestId). GET also gained try/catch parity so unexpected assembly faults surface as the masked correlated envelope instead of a raw framework crash page.
3. **Cookie behavior preserved byte-for-byte.** `applyLocaleCookie(NextResponse.cookies.set)` was replaced by a single wire-format builder consumed by BOTH branches (redirect response and plain-envelope `Response`): `NEXT_LOCALE=<whitelisted locale>; Path=/; Max-Age=31536000; SameSite=Lax[; Secure]` — identical attribute set incl. deliberately NON-httpOnly (proxy.ts jar consistency). Locale values are whitelist-validated before entering the header (no injection input). Origin allow-list, `Sec-Fetch-Site` fallback, open-redirect guard: unchanged verbatim (pinned by tests).
4. **Frontend compatibility verified.** `LocaleSwitcher` POSTs and ignores the body (`response.ok`-class flow + refresh); `useLanguageSwitch` GETs a redirect. Neither parses the old shapes (`{success:true,locale}` / `{error:"<string>"}`), so the envelope migration is non-breaking.

## 5. Traps surfaced & prevented (carry-forward)

1. The 3.1 lesson repeated itself faithfully: type-only `NextRequest` import in a file that CONSTRUCTS one detonates at runtime (`ReferenceError`) while tsgo stays silent — now codified as a guard comment in the test file header imports (outcome/3.1-outcome.md §3 pattern claimed its second victim candidate and was caught pre-runtime).
2. DOM `RequestInit` ≠ Next `RequestInit`: declaring `const init: RequestInit` breaks assignability over `signal?: AbortSignal|null`; inline constructor literals get correct contextual typing without assertions.
3. Correlated-log bag vs body distinction: whitelisted scalars (`errorName/errorMessage/errorKind`) legitimately appear ONLY in the server-side log bag; the zero-leak scan belongs to the client-facing body. Pinned accordingly.
