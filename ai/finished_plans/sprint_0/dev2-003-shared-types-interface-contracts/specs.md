# Requirements & Specification: DEV2-003 — Shared Types & Interface Contracts

## 1. Executive Summary & Problem Statement

- **Feature**: The Cross-Stream Contract Type Substrate for Kottaby LMS. This ticket defines the canonical TypeScript contract type library (`backend/types/contracts/`) that encodes, at the type level, the six cross-stream interface contracts documented in `docs/planning/TEAM_ALLOCATION.md` (Contract 1: Session Creation, Contract 2: Teacher Availability, Contract 3: Session Completion & Escrow, Contract 4: Evaluation Sessions, Contract 5: Parent Notifications, Contract 6: Admin Operations/Audit). These contracts are the shared vocabulary that Dev 1 (Student & Parent), Dev 2 (Teacher Lifecycle), and Dev 3 (Matching, Escrow & Admin) code against for every integration point in Sprints 1–3. The ticket is **substrate-only**: it ships types, composition rules, conformance tests, and canonical documentation — no database schema changes, no GraphQL resolvers, no UI.
- **Problem from user perspective**:
  - **Dev 1 (implements DEV1-005..DEV1-017)**: needs statically verifiable shapes for balance-hold requests (Contract 1 input) and the parent-session-notification payload (Contract 5 output) without coupling to Dev 3's internals.
  - **Dev 2 (implements DEV2-004..DEV2-019)**: needs the availability snapshot shape (Contract 2) and the evaluation-session shape (Contract 4) that Dev 3's matching and session engines will consume.
  - **Dev 3 (implements DEV3-004..DEV3-026)**: needs the dual-confirmation/escrow trigger type (Contract 3) that is impossible to construct without both confirmation timestamps, and the audit-write contract (Contract 6) every admin mutation must satisfy.
  - **Tech Leads / Reviewers**: need a single authoritative location where the inter-stream data boundaries are encoded, so that a breaking change to a contract produces a compile-time failure across all three streams rather than a runtime integration defect discovered in Sprint 4.
- **Business value**: All 6 cross-stream interface contracts are on the critical path for Milestones M1–M3 (per `docs/planning/ROADMAP.md` — "Define contracts in M0; integration tests in every sprint" is the stated mitigation for the **#1 risk**: "Cross-stream interface contract mismatch, Probability: Medium, Impact: High"). Mismatch discovered late costs whole-stream stalls; encode-once-as-types in Sprint 0 converts integration risk into `tsgo` errors. This is also the enforcement point where resolved decisions (B.2/B.3/B.4 escrow, B.10 on-demand, B.16 request preference, C.3 evaluator/evaluated split, A.4 notifications, A.5 audit) become machine-checkable, and where the write-path idempotency mandate (`docs/IDEMPOTENCY.md`) and financial-immutability rules (INV-W6/INV-PAY2) get their shared type-level form.
- **Actors involved**:
  - **Producers/Consumers**: `SessionService`/`MatchingService` (Dev 3, DEV3-004/DEV3-008), `SubscriptionService`/quota & balance services (Dev 1, DEV1-007), `TeacherVerificationService`/evaluation services (Dev 2, DEV2-006/DEV2-007/DEV2-011), `NotificationService` (Dev 3, DEV3-010), `ParentPortalService` (Dev 1, DEV1-016/DEV1-017), `AdminGovernanceService`/`AuditService` (Dev 3, DEV3-016/DEV3-020).
  - **Downstream consumers**: Pothos resolvers in later tickets (must import contract types — never define resolver-local parallels), GraphQL codegen (frontend consumes operation-derived types only), E2E/integration suites (DEV1-018/019, DEV3-025) that will assert contract conformance.
- **Non-goals** (explicitly OUT of scope):
  - No database schema changes (schema/foundation is DEV1-001, already implemented); no new tables, columns, indexes, or enums; `bun run db push` is NOT required by this ticket.
  - No GraphQL schema/Pothos resolver implementation (object/mutation exposure of these contracts belongs to DEV3-004+, DEV3-008+, DEV3-010+, DEV3-016+); the only GraphQL work allowed is registering nothing new — contract types are consumed by resolvers later.
  - No frontend UI, stores, or view-layer code; frontend stays on codegen-derived types (`frontend/graphql/generated/gql/graphql`).
  - No re-definition or duplication of DEV1-001 canonical entity types (`*SelectType`, `*InsertType`, `*ReturnType`, `*SubmitInput`) or DEV1-002/DEV1-003 types (`RegistrationSubmitInput`, `RecitationReading`, etc.) — contracts MUST compose them.
  - No restructuring/migration of existing `backend/enum/**` or `backend/types/**` files; no new Pothos enum registrations; `bun run generate:gqlSchema && bun codegen` output MUST be byte-identical before and after this ticket (verified by a mandated no-drift check, REQ-061).
  - No runtime service logic, no DB-repository methods, no transactions/locks (atomicity lands with consumers: DEV3-013 escrow, DEV1-007 balances).
  - No changes to `docs/planning/TEAM_ALLOCATION.md` contract prose; the types must match it, not amend it.

## 2. Requirements & Acceptance Criteria (EARS Format)

### 2.1 Baseline & Foundational Preparation (MANDATORY)

- **REQ-001 (Pre-Implementation Baseline & Ledger)**: WHEN implementation begins THEN the system SHALL record baseline error counts (`bun tsgo`, `bun biome:check`, `bun run scripts/lint-service.ts --json --id baseline`) AND initialize `ai/plans/dev2-003-shared-types-interface-contracts/deferred-items.md` from `.agents/spec-process-guide/templates/deferred-items-template.md` AND write `outcome/phase0-baseline-outcome.md`. Post-implementation, `bun tsgo` MUST report zero new errors versus baseline (a contract-type ticket that regresses type-check health defeats its purpose).
- **REQ-002 (Type-Safe i18n & Enum Value Imports Compliance)**:
  - IF any client-facing surface is later built on these contracts THEN client code SHALL use `useAppTranslation(Translation.<Namespace>)` with property access (`t.property`), never `t('key')` or namespace string literals; server components SHALL use `await getTranslations(locale)` (single argument); resolvers SHALL use `ctx.t("namespace")`. (This ticket itself introduces zero user-facing strings — verified by scan.)
  - WHEN contract types reference domain enums (`SessionStatus`, `SessionType`, `SessionIntent`, `NotificationType`, `TransactionType`, `TransactionStatus`, `TeacherRequestPreference`, `UserRole`) THEN the import SHALL be a value-or-type import from `@/backend/enum/<subdir>/...` consistent with usage, and contract documentation signatures SHALL use enum members (e.g., `SessionIntent.Hifz`), never raw string literals (`"hifz"`).
  - WHEN a contract needs a runtime-discriminating constant (e.g., a fixed `transactionType` for the wallet-credit contract) THEN it SHALL reference the enum member value via the canonical enum; a literal-carrying contract constant is PROHIBITED.
- **REQ-003 (Canonical Types Discipline)**: WHEN any contract type is authored THEN it SHALL live exclusively in `backend/types/contracts/<domain>.contract.types.ts` (one barrel `backend/types/contracts/index.ts` re-exported from `backend/types/index.ts`), SHALL build by composition (`Pick` / `Omit` / intersection) from the canonical DEV1-001 types (`@/backend/types/...`: `SessionSelectType`, `WalletSelectType`, `TeacherTransactionSelectType`, `NotificationSelectType`, `AuditLogSelectType`, `EvaluationSelectType`, `TeacherSelectType`, `StudentSelectType`) and canonical enums, and SHALL NOT redeclare any column field inline. Zero local type definitions may be created later in Pothos resolvers that shadow these contracts. `DBTransaction` / `DBQueryExecutor` SHALL be imported from `@/backend/types` only; no redefinition.

### 2.2 Core Feature Logic / Happy Paths — Contract Library

**Directory & governance:**

- **REQ-010 (Contracts Directory & Barrel Integrity)**: WHEN the contract library is created THEN the system SHALL introduce exactly one new subtree `backend/types/contracts/` containing per-contract files named `<topic>.contract.types.ts`, a barrel `backend/types/contracts/index.ts` using ONLY `export * from "./<file>"` relative paths (no `@/` aliases, no `../`, max one `/` per export path, no `import` statements), and SHALL wire `export * from "./contracts";` into `backend/types/index.ts`.
- **REQ-011 (Composition-Only Rule)**: WHEN defining any contract field whose source is a schema column THEN the type SHALL obtain it via `Pick`/`Omit`/intersection of the canonical `*SelectType` / `*ReturnType`; redefining the column's type (e.g., writing `fee: number` when `SessionSelectType.fee` is `string | null` from `decimal`) is PROHIBITED and SHALL fail the conformance suite (REQ-070).
- **REQ-012 (Contract Documentation Headers)**: WHEN a contract type ships THEN its file SHALL carry a JSDoc header citing: the `docs/planning/TEAM_ALLOCATION.md` Contract # (1–6), the owning/consumer streams, and the governing decision refs from `docs/specs/open-decisions-and-gaps.md` (e.g., `B.4`, `C.3`).

**Contract 1 — Session Creation (Dev 1 → Dev 3; `session-request.contract.types.ts`):**

- **REQ-013 (SessionRequestContract)**: WHEN a student-side service hands a session-creation instruction to the session engine THEN the call SHALL be typed as `SessionRequestContract` comprising exactly: `studentId` and `teacherId` (from `SessionSelectType`), `intent` (`SessionIntent`, non-null — Decision A.10), `sessionType` constrained to `SessionType.StudentSession` (Decision A.8 — evaluation sessions MUST go through Contract 4, REQ-017), `fee` and `feeHeld` (from `SessionSelectType`; at request time `feeHeld` is the literal `true` — Decision B.4 hold-at-request), `confirmationDeadline` (from `SessionSelectType`; Decision B.2 — NOW()+24h), and `idempotencyKey` (`string`, per `docs/IDEMPOTENCY.md` §Affected Operations). All fields SHALL be `readonly`.
- **REQ-014 (Balance Eligibility Out-of-Contract)**: IF a request lacks balance THEN the rejection SHALL be a domain error at the consuming service (DEV1-007/DEV3-013, INV-B4) — `SessionRequestContract` SHALL NOT carry balance state (balances are Dev 1's ledger concern and change post-request); a `balance*` field on the contract is PROHIBITED (guards Decision B.4 separation of hold vs. decrement).

**Contract 2 — Teacher Availability (Dev 2 → Dev 3; `teacher-availability.contract.types.ts`):**

- **REQ-015 (TeacherAvailabilitySnapshotContract)**: WHEN the matching engine (DEV3-008) consumes teacher availability THEN the snapshot type SHALL comprise: `teacherId`, `isOnline`, `averageRating`, `subjects` (JSON-string per DEV1-001 `teacher.subjects` — the contract SHALL define `TeacherSubjectsParsed = string[]` as the parse target and a module-level parser signature requirement, without changing the schema), `requestPreference` (`TeacherRequestPreference`; Decision B.16), plus matcher-relevant `country` and language fields sourced from `UserSelectType`/`StudentSelectType` by `Pick`. Fields SHALL be `readonly`. The type SHALL be documented as a point-in-time snapshot (Decision B.15 staleness ≤15min is enforced by Dev 2's toggle/timeout logic, not by this type).
- **REQ-016 (In-Session Exclusion Marker)**: WHEN a teacher is in a `started` session THEN the contract SHALL express exclusability via the snapshot only (`isOnline: false` per INV-A2/INV-S6) — the contract SHALL NOT introduce a parallel "inSession" flag, ensuring matching has a single availability source (INV-A3).

**Contract 4 — Evaluation Sessions (Dev 2 → Dev 3; `evaluation-session.contract.types.ts`):**

- **REQ-017 (EvaluationSessionContract)**: WHEN the evaluation loop (DEV2-006) books an evaluation session THEN the contract SHALL constrain `sessionType` to the literal union containing `SessionType.TeacherEvaluation` or `SessionType.ReEvaluation` and `intent` to `SessionIntent.Evaluation`, SHALL carry `evaluatedId` and `evaluatorId` from `EvaluationSelectType` (Decision C.3 — both are FKs to `users.id`, never `teacher.id`), and SHALL expose `completedEvaluatorIds: readonly id-list` as the INV-TV2 distinct-evaluator evidence shape delivered to the aggregation step (DEV2-007). `evaluatedId === evaluatorId` SHALL be rejected by a consuming-service rule reference in the contract docs.

**Contract 3 — Dual Confirmation & Escrow (Dev 3 → Dev 1 & Dev 2; `session-completion-escrow.contract.types.ts`):**

- **REQ-018 (DualConfirmationContract)**: WHEN a session reaches `completed` THEN the confirmation state SHALL be typed `DualConfirmationState` (`confirmedByTeacherAt`, `confirmedByStudentAt`, `confirmationDeadline` from `SessionSelectType`), and the escrow trigger SHALL be typed `EscrowTriggerContract` whose construction REQUIRES BOTH confirmation timestamps to be non-null at the type level (e.g., non-nullable branded fields) such that releasing escrow without dual confirmation is a compile-time error (INV-S3, Decision B.2).
- **REQ-019 (WalletCreditContract — Immutable Earning)**: WHEN dual confirmation completes THEN the crediting instruction SHALL be typed `WalletCreditContract`: `walletId`, `sessionId` (non-null, per INV-W7 earnings link), `amount` (from `TeacherTransactionSelectType.amount`, non-negative by INV-W8 and DB check), `type` constrained to `TransactionType.Earning`, `status` constrained to `TransactionStatus.Completed`, plus `idempotencyKey`. The type SHALL be `readonly` at every depth and SHALL carry a doc note that financial records are immutable post-insert (INV-W6, INV-PAY2) — no `updateWalletCredit` shape may exist anywhere in the library.
- **REQ-020 (EscrowReleaseContract — Cancellation Path)**: WHEN a session is cancelled or the 24h confirmation deadline lapses (B.2 auto-cancel) THEN the release instruction SHALL be typed `EscrowReleaseContract` carrying `sessionId`, `releaseReason` (`CancellationConfirmed | ConfirmationTimeout` — backed by a canonical enum or a literal union localized only in this file and reused by DEV3-012/013), and `idempotencyKey`; carrying a wallet-credit payload SHALL be a compile-time impossibility (no amount field, no walletId field).

**Contract 5 — Parent / Session Notifications (Dev 3 → Dev 1; `session-notification.contract.types.ts`):**

- **REQ-021 (SessionEventNotificationContract)**: WHEN the notification engine (DEV3-010) persists a session lifecycle event THEN the payload SHALL be typed via `SessionEventNotificationContract` composed from `NotificationSelectType`: `userId` (recipient), `type` (`NotificationType` — SessionRequest, SessionCompletion, SessionCancellation only for this contract; `ParentLinkRequest`, `SystemBroadcast`, `PaymentConfirmation`, `EvaluationResult` are handled by sibling contracts in the same file), `relatedEntityType` + `relatedEntityId` (polymorphic pointer; type SHALL require both or neither), and SHALL NOT expose `isRead` (system-managed) in the input shape (A.4).

**Contract 6 — Admin Audit (Dev 3 → all; `admin-audit.contract.types.ts`):**

- **REQ-022 (AuditLogWriteContract)**: WHEN any admin-governed mutation (DEV3-016.. DEV3-022d, DEV2-010/018) executes THEN the audit write SHALL be typed `AuditLogWriteContract` composed from `AuditLogSelectType`-compatible fields: `actorId`, `actionType` (`AuditActionType`), `entityType`, `entityId`, `details` (JSON-safe string, ≤2000 per schema), and SHALL NOT accept `id` or `createdAt` (system-set). The contract doc SHALL state append-only semantics (A.5; audit rows must never be updated).
- **REQ-023 (Cross-Stream Auth Stance Types)**: WHEN contracts carry actor data THEN an `ActorContextRef` shape (`userId`, `role: UserRole`) SHALL be provided as the minimal identity hand-off between streams, and it SHALL NOT contain email, phone, or any credentials.

**Library-wide invariants:**

- **REQ-024 (Readonly Discipline)**: WHEN any contract field is declared THEN it SHALL be `readonly`, and collection fields SHALL be `readonly T[]`/`ReadonlyArray<T>`; drafts must never be mutated downstream.
- **REQ-025 (No UI Leakage)**: WHEN the contract library is complete THEN a structural test SHALL verify no contract type references MUI/React/i18n-label types and no file under `backend/types/contracts/` imports from `@/frontend/**`, `@/app/**`, or shares a barrel with such code.
- **REQ-026 (Gherkin Acceptance — Compile-Time Authority)**: GIVEN the shared types module is installed, WHEN any stream's service imports a contract type, THEN all six TEAM_ALLOCATION interface contracts SHALL be expressible with zero `any`, zero inline redefinitions, and `bun tsgo` exit code 0 across the repo.
- **REQ-027 (Idempotency Uniformity)**: WHEN any contract represents a mutating create (SessionRequest, WalletCredit, EscrowRelease) THEN an `idempotencyKey: string` field SHALL be mandatory; consumer tasks (DEV3-004/013) SHALL be documented as the enforcement point for the 409/DUPLICATE_REQUEST behavior per `docs/IDEMPOTENCY.md` (this ticket ships the field, not enforcement).
- **REQ-028 (Single-Shapes Rule)**: IF a future endpoint needs a subset of a domain type for an API body THEN it SHALL derive from the matching contract or canonical type via `Pick`/`Omit` in `backend/types/**` — duplicating a contract's shape in `services/` (service-layer `.types.ts` are PROHIBITED repo-wide) or resolvers is forbidden.
- **REQ-029 (Decision Anchoring)**: WHEN a contract encodes a resolved decision THEN the JSDoc SHALL cite its ID (`A.4`, `A.5`, `A.8`, `A.10`, `B.2`, `B.3/B.4`, `B.16`, `C.3`), and the conformance suite SHALL contain one compile-time anchor per cited decision (see REQ-070).

### 2.3 Security, Authorization & Type-Level Tenancy

- **REQ-030 (Forbidden-Field Exclusions)**: WHEN any contract type is authored THEN the following fields SHALL be structurally absent (enforced by `Omit` on source types and by conformance negative tests): `passwordHash` (and any credential/refresh-token fields), user governance flags (`isDeleted`, `deletedAt`, `suspended`, `suspendedAt`, `suspendedPeriodDays`, `isBlocked`, `blockedAt` — Decision A.7 keeps governance at `users`, never in inter-stream contracts), and session-balance ledger columns (`balanceHifz`, `balanceTajweed`, `balanceReviews` — REQ-014).
- **REQ-031 (BOPLA Whitelist Form)**: WHEN a contract type represents caller-supplied intent (SessionRequestContract, AuditLogWriteContract admin input portion) THEN it SHALL be a closed `readonly` interface with an explicit field list; `{ ...input }` spreads of these types into Drizzle inserts are PROHIBITED for all future consumers (stated as a binding rule; enforcement continues via BOPLA audits in consumer tickets and REQ-070 static scan for `...`adjacent usage anti-pattern in the library itself).
- **REQ-032 (BFLA Type Separation)**: WHEN admin-privileged operations are typed (`AdminGovernanceContract` surfaces for DEV3-016+) THEN they SHALL live in a dedicated file (`admin-audit.contract.types.ts` / future `admin-governance.contract.types.ts`) with no re-export path that bundles them into student-facing contract files; mixed barrels that would let a student-flow module import admin contracts by accident are PROHIBITED.
- **REQ-033 (Tenancy Fields Mandatory)**: WHEN a contract could ambiguously reference an entity across actors (sessions, notifications) THEN ownership identifiers SHALL be required non-nullable fields (`studentId`, `teacherId`, `userId`, `parentId` where applicable); identifier-less "fetch-anything" shapes are PROHIBITED. This is the type-level grounding of BOLA/IDOR assertions which consumers enforce at runtime (`ctx.user.id` ownership checks).
- **REQ-034 (No Secrets in Contracts)**: IF a contract could transitively carry payment references THEN it SHALL include only the DEV1-001 `subscriptions` payment-audit fields as `Pick`s (`paymentReference`, `paymentMethod`, `paymentVerifiedAt` per Decision B.9) and SHALL never expose gateway secrets, tokens, or raw card data.
- **REQ-035 (Rate-Limit & Wildcard Note)**: This ticket adds no searchable endpoints; consumers of any future `search`-bearing contract SHALL apply `escapeLikeWildcards` before LIKE/ILIKE use (binding rule referenced from this spec into consumer plans); rate limiting is not applicable to a types-only deliverable beyond inheriting the platform's existing fail-open stub posture (DEV2-002 owns real limits).

### 2.4 Atomicity, Concurrency & Data Integrity (Type-Level)

- **REQ-040 (Hold/Release Pairing)**: WHEN escrow lifecycle is typed THEN `EscrowReleaseContract` SHALL reference the hold by required `sessionId` (and optional `holdIdempotencyKey`) so a release cannot be typed without identity of the hold it reverses; a release-without-hold-identity shape MUST NOT be expressible.
- **REQ-041 (Point-in-Time Snapshot Semantics)**: WHEN `TeacherAvailabilitySnapshotContract` is documented THEN it SHALL state that it is a point-in-time read; the TOCTOU guard (re-assert `isOnline`/`is_approved` inside the session-creation transaction, plus INV-S5 certified-teacher check at creation) is delegated to DEV3-004/DEV3-008 services and SHALL be called out in the contract JSDoc so consumers do not mistake the snapshot for a lock.
- **REQ-042 (No Transaction Logic in Types)**: WHEN implementation is complete THEN `backend/types/contracts/**` SHALL contain zero runtime code beyond pure type guards/assertion helpers; no `DBTransaction` usage, no queries, no `runInRollback` touchpoints (DB tests are N/A for this ticket — see REQ-072).
- **REQ-043 (Dual-Confirmation Race Encoding)**: WHEN either party confirms THEN the resulting `DualConfirmationState` update shape SHALL be a partial advancing only the caller's timestamp; the escrow trigger type (REQ-018) SHALL NOT be constructible from two independent half-confirms without reading back the stored row (the JSDoc SHALL mandate read-modify-write via the DB state machine, implemented in DEV3-012) — encoding the rule that confirmation is DB-state-derived, not caller-computed.
- **REQ-044 (Unique/Idempotent-Reentry Awareness)**: WHEN contracts with `idempotencyKey` are consumed THEN the documented expectation SHALL be that a repeated key returns the already-created entity (not a second insert), aligning with DEV1-002's 23505→`ConflictError` translation via `Error.cause` chain traversal (`docs/auth/user-registration.md` §6) and `docs/IDEMPOTENCY.md`; the type library SHALL include a shared `DuplicateKeyViolation` contract reference note but no translation logic.

### 2.5 Validation & Error Contracts

- **REQ-050 (DomainError Alignment)**: WHEN contract-adjacent validation fails in future consumers THEN errors SHALL be thrown as `DomainError` subclasses from `backend/lib/errors.ts` with `SCREAMING_SNAKE_CASE` `extensions.code` per `docs/graphql/domain-error-extensions-code.md`; this ticket's contribution is the typed catalog `ContractErrorCodes` (const object) enumerating ONLY codes this substrate's own guards/canonicalization produce (e.g., `CONTRACT_SUBJECTS_PARSE_INVALID`), localized via `shared/locale` at throw time — never string messages embedded in the library.
- **REQ-051 (Localized-Only Rule)**: WHEN any message is needed by a contract helper (e.g., subjects parser rejection) THEN it SHALL be a translation-key reference resolved by the caller via `getServerTranslations(locale, "<namespace>")` or `ctx.t(...)`; hardcoded user-facing or error strings in `backend/types/contracts/**` are PROHIBITED and scanned in REQ-070.
- **REQ-052 (Guard Return Shapes)**: WHEN runtime guards ship (e.g., `parseTeacherSubjects(raw)`, `isEvaluationIntent(value)`) THEN they SHALL return either the parsed canonical value or throw a `ValidationError` with a localized message — boolean-returning `is*` predicates plus `assert*` variants are the ONLY second pattern allowed; silent `null` swallowing of invalid enum values is PROHIBITED.
- **REQ-053 (Enum Strictness at Boundaries)**: WHEN unknown strings arrive at a contract boundary THEN canonicalization SHALL use the DEV1-001 enum value sets; the library SHALL not normalize loose inputs ("HIFZ" → `hifz`) unless a dedicated documented mapper exists — unknown values MUST fail closed with `ValidationError`.

### 2.6 GraphQL & Frontend Contracts

- **REQ-060 (No Pothos Drift)**: WHEN this ticket completes THEN no changes SHALL exist under `backend/graphql/**`; future resolvers consuming contracts SHALL import from `@/backend/types` (NEVER resolver-local redeclarations — repo CRITICAL RULE); if a contractual field needs GraphQL exposure later, the Pothos type MUST reference the canonical/contract type.
- **REQ-061 (Schema/Codegen No-Op Gate)**: WHEN pre- and post-implementation outputs of `bun run generate:gqlSchema && bun codegen` are compared THEN they SHALL be byte-identical; any diff FAILS the ticket (proves substrate-only scope).
- **REQ-062 (Frontend Boundary)**: WHEN frontend code needs these concepts THEN it SHALL use GraphQL codegen operation types only; `frontend/**`/`app/**` SHALL NOT import from `@/backend/types/contracts/**`. IF a genuinely cross-layer contract emerges in later tickets (e.g., a shared view-model) THEN it SHALL be added to `shared/types/<domain>.types.ts` in THAT ticket per `docs/backend/shared-types-pattern.md` — none is added here (documented as an explicit deferred decision, logged in `deferred-items.md` only if a consumer actually needs it; otherwise: no entry).
- **REQ-063 (Future `id`-Field Propagation)**: WHEN contracts surface through GraphQL later THEN consumer tickets SHALL include `id` fields on every object selection for Apollo normalization (restated as binding guidance — the types have `id` via the canonical source types already).

### 2.7 Test Coverage

- **REQ-070 (Compile-Time Conformance Suite)**: WHEN the test suite is designed THEN a compile-time conformance file SHALL exist at `backend/types/contracts/contracts.conformance.test-d.ts`-style coverage (type-level) PLUS a runtime guard spec at `backend/types/contracts/contract-guards.test.ts`, such that: (a) every REQ-013..REQ-023 contract has a positive `satisfies` construction test using canonical fixtures; (b) every REQ-030 exclusion has a negative `@ts-expect-error` test (e.g., assigning `passwordHash`, missing dual timestamps, earning without `sessionId`, string literal instead of `SessionIntent.Hifz`); (c) `bun tsgo` MUST fail if (a) breaks or (b) unexpectedly compiles — the suite IS the PR-review enforcement for "type changes require cross-stream review."
- **REQ-071 (Runtime Guard Coverage)**: WHEN guard helpers run THEN tests SHALL hit Tier-1 (100% statement/branch on every guard), Tier-2 (boundaries: empty subjects string, malformed JSON, `""`, `null`, undefined in `amount`/`sessionId`-carrying payloads, unicode/RTL strings for entityType), Tier-3 (fuzz: randomized non-enum strings against `is*`/`assert*` guards; concurrent `Promise.allSettled` parse storms to prove guards are stateless), and Tier-4 (abuse: SQL/LIKE wildcards `"%"`, `"_"`, `"\\"` and control chars rejected at enum/subject boundaries — REQ-053).
- **REQ-072 (Testing Constraints)**: BECAUSE this ticket has zero DB surface, `runInRollback`/`tx` rules are NOT applicable and SHALL be marked "N/A — substrate ticket" in tasks; repository tests, `expectRepoError`, and DB coverage gates apply starting at consumer tickets (DEV1-007+, DEV3-004+), which SHALL reference these contracts in their own test plans.
- **REQ-073 (Forbidden-Pattern Static Assertions)**: WHEN the conformance suite runs THEN it SHALL include file-content assertions (or a scripted check) that no file in `backend/types/contracts/**` contains: `any` (outside narrowly-scoped guard internals), string-literal duplicates of enum values, hardcoded user-facing strings, `import ... from "@/frontend`" / `"@/app"`, `{ ...spreadIntoInsert }` patterns, or non-`readonly` exported mutable values.
- **REQ-074 (Baseline Delta Gate)**: WHEN implementation ends THEN `bun tsgo` error count and `bun biome:check` warning count SHALL equal baseline (REQ-001) plus zero; the final gate SHALL also re-run REQ-061 (codegen no-drift) and record both results in the completion outcome.

### 2.8 Documentation & Knowledge Gates

- **REQ-080 (Canonical Doc)**: WHEN the library lands THEN a canonical reference doc SHALL be created at `docs/backend/cross-stream-contracts.md` containing: the six contracts (TEAM_ALLOCATION §1–6 mirrors), the composition-only rule, forbidden-field registry, decision/invariant mapping table (REQ-082), consumer-ticket wiring list (DEV1-007, DEV2-006/007/011, DEV3-004/008/010/012/013/016/020), and the "@ts-expect-error conformance" pattern guide for future contract evolution.
- **REQ-081 (AGENTS.md Propagation)**: WHEN propagation runs THEN: `backend/types/AGENTS.md` SHALL gain a "Contracts Subtree" rule (1–2 lines + doc link); root `AGENTS.md` Important References SHALL add `docs/backend/cross-stream-contracts.md`; `shared/AGENTS.md` shall be touched ONLY if REQ-062 changes (it does not in this ticket — record "no change" in outcome); no implementation details may be embedded in AGENTS.md entries.
- **REQ-082 (Invariant Pinning)**: WHEN the doc is written THEN every contract SHALL be mapped to its invariants from `docs/specs/state-machine-invariants.md` (Session INV-S1..S8, Teacher-availability INV-A1..A4, Wallet INV-W1..W8, Payment INV-PAY1..PAY5, Verification INV-TV1..TV7, Parent INV-P1..P4) and its workflow (`docs/workflows/02/03/04/05`), giving consumers a single lookup for "types ↔ rules."
- **REQ-083 (Change Governance Statement)**: WHEN teams modify a contract type THEN the doc SHALL require: (1) conformance-suite update in the same PR; (2) PR review by all affected stream owners (mirrors `docs/planning/TEAM_ALLOCATION.md` "Contract changes" rule); (3) a note in that ticket's `deferred-items.md` only if cross-ticket coordination is deferred — otherwise never.

## 3. System Decisions & State Machine Invariants Alignment

- **Decision References (`docs/specs/open-decisions-and-gaps.md`)**:
  - **A.4 (notifications table)**: Drives REQ-021 (`SessionEventNotificationContract` composed from `NotificationSelectType`; `notification_type` enum values gate which contracts exist per event class).
  - **A.5 (audit_logs, append-only)**: Drives REQ-022 (`AuditLogWriteContract`; no id/createdAt acceptance; append-only documented).
