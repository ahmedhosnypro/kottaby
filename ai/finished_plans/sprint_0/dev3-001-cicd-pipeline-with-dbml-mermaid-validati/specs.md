# Requirements & Specification: DEV3-001 — CI/CD Pipeline with DBML & Mermaid Validation

## 1. Executive Summary & Problem Statement

- **Feature**: DEV3-001 delivers the project's mandatory Continuous Integration gate: a CI pipeline that runs on every Pull Request targeting `develop` (and on pushes to `develop`/`main`), executing — in enforced order — lint/type/format checks (the same mechanical checks as `bun quality-gate`: `tsgo` → `oxlint` → `biome:check` → `lint` → `check:duplicates`), structural documentation validation (`bun validate:dbml` on `db/schema.dbml`; `bun run scripts/validate-mermaid.ts` on changed `.mmd`/`.md` documentation files), and the automated test suites in scope for pull requests. The PR **cannot be merged** unless every required check is green. This ticket is infrastructure-only: it ships workflow definitions, supporting script wiring, caching configuration, and verification evidence — no application domain logic.
- **Problem from user perspective**:
  - **Dev 1 / Dev 2 / Dev 3 (feature developers)**: Without enforced PR gates, schema drift (DBML ↔ Drizzle), broken Mermaid diagrams (the 20+ validated blocks in `docs/`), lint regressions, and failing tests merge silently into `develop` and poison downstream streams. Each developer needs a fast, deterministic, clearly-attributed failure signal before review.
  - **PR Reviewers / Tech Lead**: Reviews must not waste cycles on mechanically-detectable defects. Reviewers open a PR only after CI is green; a red pipeline with precise per-file/per-rule output is the first review.
  - **Orchestrator / subagent executors (spec-implementation workflow)**: All local quality work flows through `scripts/health/sub-loop.ts` and `bun quality-gate`; CI must re-execute the *same* truth remotely so "passed locally" cannot diverge from "passed in CI".
  - **Product/Platform integrity**: The planning suite (`docs/planning/PRODUCTION_READINESS.md`, ROADMAP M0 gate) requires "CI/CD green" as a release gate. The 33 resolved decisions and 50+ state-machine invariants are only durable if every merge is forced through validation.
- **Business value**: Prevents broken schema contracts, stale documentation, and failing tests from reaching the integration branch; establishes the merge-blocking enforcement every subsequent Sprint 0–4 ticket depends on; protects the financial/state-machine invariant test suites (present and future) by making them non-bypassable; reduces post-merge firefighting and rework cost.
- **Actors involved**:
  - **Callers**: Developers opening/updating PRs; orchestrator agents validating plan outputs; GitHub branch protection evaluating merge eligibility.
  - **Downstream consumers**: All future DEV1/DEV2/DEV3 tickets (their tests and schema/diagram changes run under this pipeline); `docs/planning/PRODUCTION_READINESS.md` launch gate (requires green CI evidence).
- **Non-goals** (explicitly OUT of scope for DEV3-001):
  - **Deployment / CD**: No deploy targets, release pipelines, containerization, or environment promotion. `main` merges are gated, not deployed.
  - **Live provider integration smokes**: `test/integration/**` (Resend, Twilio, FCM, Fixer, Zoom, etc.) is excluded per `test/integration/AGENTS.md` ("`test:integration` is NOT part of default CI"). No live API keys are provisioned in CI.
  - **Playwright E2E / production-build UI tests**: `test:ui:e2e` (requires `bun run build:test` and a server lifecycle) is deferred; component tests (`test:ui:components`) are in scope. E2E-in-CI lands with a later Sprint 4 hardening ticket.
  - **Scheduled/cron workflows** (nightly jobs, drift monitors, dependency update bots).
  - **Code coverage threshold enforcement** beyond what the test runners themselves assert (repository-layer 100% coverage targets are enforced by suite discipline, not a CI coverage gate in this ticket).
  - **Self-hosted runners** and any cloud infrastructure provisioning.
  - Modifying application source code, GraphQL schema content, or database schema content (the pipeline *validates*; it does not *change* domains).

## 2. Requirements & Acceptance Criteria (EARS Format)

### 2.1 Baseline & Foundational Preparation (MANDATORY)

- **REQ-001 (Pre-Implementation Baseline & Ledger)**: WHEN implementation begins THEN system SHALL record baseline error counts (`tsgo` error count, `biome:check` warning count, `lint-service --json` output) and initialize `ai/plans/dev3-001-ci-cd-pipeline/deferred-items.md` from `.agents/spec-process-guide/templates/deferred-items-template.md`. The baseline (including `git diff --name-only` to distinguish pre-existing modifications) SHALL be written to `ai/plans/dev3-001-ci-cd-pipeline/outcome/phase0-baseline-outcome.md`.
- **REQ-002 (Type-Safe i18n & Enum Value Imports Compliance)**:
  - IF any user-facing string is introduced by this ticket's supporting TypeScript (e.g., a CLI error line in a validation wrapper), THEN the system SHALL source it from the compile-time i18n system (`shared/locale/`) — server/script contexts use `getServerTranslations(locale, "namespace")` from `@/shared/locale/server-graphql`; client components are out of scope; GraphQL resolvers are out of scope.
  - WHEN enums are referenced in any new TypeScript runtime expression or cast THEN the system SHALL use value imports (never `import type`) and enum members (never raw string literals).
  - IF a workflow file (YAML) contains human-readable messaging THEN it MAY use English inline (CI logs are operator-facing, not user-facing; i18n does not apply to GitHub Actions YAML) — this explicit exemption SHALL be recorded in the plan outcome.
- **REQ-003 (Canonical Types Discipline)**: IF new TypeScript files are added under `scripts/` THEN they SHALL import shared types from `@/backend/types` (never define ad-hoc local domain types), SHALL never import from `@/frontend/**` or `@/app/**` into `shared/`, and SHALL use the in-process lint service API (`requestLint` / `requestFullRepoLint` from `@/scripts/lint-service`) rather than spawning ad-hoc ESLint processes when programmatic lint invocation is needed.

### 2.2 Core Feature Logic / Pipeline Happy Paths (REQ-010..REQ-029)

- **REQ-010 (Trigger Coverage)**: WHEN a pull request targeting `develop` or `main` is opened, synchronized, reopened, or marked ready-for-review THEN the CI pipeline SHALL execute automatically. WHEN a commit is pushed to `develop` or `main` THEN the same pipeline SHALL execute to guarantee post-merge branch health.
- **REQ-011 (Fork Safety Trigger)**: The pipeline SHALL NOT use `pull_request_target` for any job that checks out or executes PR-authored code. IF a PR originates from a fork THEN the workflow SHALL run with a read-only token and without repository secrets.
- **REQ-012 (Bun Runtime Pinning)**: WHEN the pipeline provisions its toolchain THEN it SHALL install Bun via the official oven-sh/setup-bun action using the exact Bun version declared by the repository (consistent with local `~/.bun/bin/bun` usage), and SHALL fail fast with a clear step message if the pinned version cannot be resolved.
- **REQ-013 (Deterministic Dependency Install)**: WHEN dependencies are installed THEN the system SHALL run `bun install --frozen-lockfile`. IF the lockfile is inconsistent with `package.json` THEN the install SHALL fail and the pipeline SHALL report the failure before any quality stage executes.
- **REQ-014 (Mechanical Quality Gate in CI)**: WHEN the quality stage executes THEN the system SHALL run the same mechanical checks that developers run locally — `bun tsgo`, `bun run oxlint`, `bun biome:check`, and `bun run lint` (the in-process serialized lint service) plus `bun run check:duplicates` — via the project's canonical entry points. IF any check exits non-zero THEN the pipeline stage SHALL fail and the failure output SHALL be surfaced in the job log.
- **REQ-015 (Check Ordering, Fail-Fast Within Stage)**: WHEN the quality stage runs THEN checks SHALL execute in the canonical order `tsgo → oxlint → biome:check → lint → duplicates`, mirroring `scripts/health/sub-loop.ts` progressive semantics, so the earliest (cheapest/most fundamental) failure is reported first. Later checks MAY be skipped after a failure within the stage.
- **REQ-016 (DBML Validation — Always Full)**: WHEN any pull request executes THEN the pipeline SHALL run `bun validate:dbml` against the repository's `db/schema.dbml` on every run (unconditionally, not only when DBML files change). IF validation fails THEN the `dbml-validation` check SHALL fail and block the merge.
- **REQ-017 (Mermaid Validation — Changed-File Scoped with Full-Set Fallback)**: WHEN a pull request modifies, adds, or deletes any file matching `**/*.mmd` or `docs/**/*.md` (or any documentation file containing Mermaid blocks) THEN the pipeline SHALL compute the changed-file set (merge-base diff against the PR target branch) and execute `bun run scripts/validate-mermaid.ts <changed files…>`. IF no documentation files changed THEN the step SHALL report a passing no-op (not skip silently) to keep the signal explicit. WHEN pushing to `develop`/`main` THEN the step MAY validate the full documentation set.
- **REQ-018 (Merge-Blocking Contract)**: WHEN the workflow completes THEN every required status check (at minimum: `quality` (REQ-014), `dbml-validation` (REQ-016), `docs-validation` (REQ-017), and `tests` (REQ-020)) SHALL appear as a distinct, named check on the PR. Branch protection / ruleset configuration guidance SHALL be documented so each named check is marked *required* — a PR cannot merge while any required check is pending or failing.
- **REQ-019 (Stage Independence & Parallelism Where Safe)**: The pipeline SHOULD structure `dbml-validation` and `docs-validation` as independent jobs running in parallel with the quality stage, because both are read-only static validators. The `tests` job SHALL NOT start before the quality stage passes (avoid wasting shared-runners on code that fails lint), EXCEPT that DB-unit tests MAY run in parallel with docs/dbml jobs.
- **REQ-020 (PR-Scoped Test Suites)**: WHEN the tests stage executes THEN the system SHALL run: `bun run test:db` (repository/logic suites, with a PostgreSQL 16 service container — see REQ-021), `bun run test:services` (service-layer suites with external adapters mocked per `backend/services/AGENTS.md`), and `bun run test:ui:components` (Happy DOM component suites). IF any suite has failing tests THEN the `tests` check SHALL fail with the per-suite summary visible in the job summary.
- **REQ-021 (PostgreSQL Service Container for DB Tests)**: WHEN `test:db` runs in CI THEN a PostgreSQL service SHALL be provisioned per-job (ephemeral, isolated), with `DATABASE_URL` pointing at the service and the test database initialized via the project's standard schema path (`bun run db push` per repo policy — `db reset` and `db cleanGenerate` are permanently disabled and SHALL NOT be used in CI (see Decision/Policy: docs/DATABASE_MIGRATIONS.md)). IF schema application fails THEN the job SHALL fail before tests run.
- **REQ-022 (Environment Hygiene for CI Runs)**: WHEN any CI job executes THEN it SHALL source its runtime environment from a CI-managed `.env.test` materialization strategy (e.g., secrets-injected or committed test-env template), SHALL set `TEST_SERVER=1` (keeping `logger.logDomainError` compact in test logs), and SHALL NOT require any live third-party credential. IF a required variable is absent THEN affected steps SHALL fail fast with a named missing-variable error rather than a downstream cryptic failure.
- **REQ-023 (Cache Strategy — Preserve, Never Clear)**: WHEN the pipeline configures caching THEN it SHALL cache the Bun global install cache and the ESLint caches (`.eslintcache`, `.eslintcache-type-aware`) with keyed restore/save (keyed by OS + lockfile hash + a per-workflow epoch prefix). The pipeline SHALL NEVER delete or invalidate these caches in-band — preserving caches mirrors the non-negotiable local rule that quality tooling caches are never cleared (`AGENTS.md` / quality-loop skill). IF a cache restore misses THEN the job SHALL proceed with cold caches and re-populate on save.
- **REQ-024 (Superseded-Run Concurrency Cancellation)**: WHEN a new commit is pushed to a PR with an in-progress pipeline run THEN the system SHALL cancel the superseded run via a concurrency group keyed by `workflow + pull_request number/ref` with `cancel-in-progress: true` for PR events. WHEN merging to `develop`/`main` THEN runs SHALL NOT auto-cancel earlier `develop` runs that are evaluating different merge commits (`cancel-in-progress: false` for branch pushes), preserving a complete per-commit audit trail.
- **REQ-025 (Timeout Bounding)**: WHEN any job executes THEN it SHALL declare `timeout-minutes` (quality ≤ 15, tests ≤ 30, docs/dbml ≤ 5 as starting budgets, tunable during implementation). IF a job exceeds its budget THEN GitHub SHALL kill it and surface a timeout failure — no job may hang the required-check signal indefinitely.
- **REQ-026 (Failure Signal Quality)**: WHEN the pipeline fails THEN the failure SHALL be attributable to a single named check in the PR checks list, and the failing step's output SHALL include the tool's native error lines (e.g., `error TS…`, biome diagnostics, ESLint JSON-text output, DBML validator messages, Mermaid validator file/line references) without truncation by wrapper scripts.
- **REQ-027 (Local↔CI Parity)**: WHEN a developer reproduces a CI failure locally THEN the documented commands in the pipeline definition SHALL be exactly the repo-local commands (`bun run lint`, `bun validate:dbml`, `bun run scripts/validate-mermaid.ts <files>`, `bun run test:db`, etc.) — no CI-only shell logic that cannot be replicated locally. IF a pipeline step requires composition (e.g., changed-file detection) THEN the composition SHALL be implemented in a committed script (under `scripts/`) so it can be run identically on a workstation.
- **REQ-028 (Pipeline Self-Documentation via Job Summary)**: WHEN each run completes THEN the workflow SHOULD write a GitHub job summary (markdown) listing: checks executed, per-check pass/fail, durations, and (on docs/dbml jobs) the set of files validated. This summary is the audit artifact referenced by release gates.
- **REQ-029 (Workflow Syntax Correctness Gate)**: WHEN the workflow YAML is modified THEN the pipeline definition SHALL be statically validated (e.g., actionlint-compatible structure — verified locally during implementation) and `bun tsgo`/`biome:check` SHALL pass over any changed scripts before merge of this ticket itself.

### 2.3 Security, Authorization & Tenancy (REQ-030..REQ-039)

- **REQ-030 (Minimal Token Permissions)**: WHEN the workflow executes THEN it SHALL declare an explicit top-level `permissions:` block granting `contents: read` (plus, only if needed, `pull-requests: write` for annotations/checks metadata alternates — default OFF unless a step demonstrably requires it). IF no step requires PR write access THEN it SHALL NOT be granted.
- **REQ-031 (No Secret Materialization on Forks)**: IF a PR originates from a fork THEN the workflow SHALL execute with zero repository secrets in scope — DB connectivity uses the ephemeral service-container credentials generated per-job, not stored secrets. WHEN secrets ARE used (non-fork runs needing env materialization) THEN they SHALL be injected via environment mapping at the step level, never echoed, and never written to `$GITHUB_STEP_SUMMARY` or artifacts.
- **REQ-032 (Action Pinning)**: WHEN third-party actions are referenced (checkout, setup-bun, cache) THEN they SHALL be pinned by immutable commit SHA (with a version comment). IF an action is unpinned or tag-pinned only THEN the plan-review/self-review SHALL flag it before merge of this ticket.
- **REQ-033 (Cache Poisoning Guard)**: WHEN PR-event runs restore/save caches THEN cache save keys for PR events SHALL be namespaced distinctly from protected-branch (`develop`/`main`) cache keys, so untrusted PR builds cannot poison the cache consumed by protected-branch builds. IF the cache action does not restore PR-written saves onto `develop` runs THEN the guard is satisfied.
- **REQ-034 (No Credential Persistance in Checkout)**: WHEN the repository is checked out THEN the step SHALL set `persist-credentials: false` unless a step explicitly requires authenticated `git` operations (none are planned). IF no such step exists THEN the flag SHALL remain `false`.
- **REQ-035 (Script Injection Defense)**: WHEN workflow expressions interpolate PR-controlled data (branch names, PR titles, commit messages) THEN they SHALL NOT be interpolated directly into `run:` shell blocks. IF such data must be used (e.g., changed-file lists) THEN it SHALL be passed through environment variables with proper quoting or computed via safe GitHub contexts (`github.event` paths for file diffs come from the VCS, not user text).
- **REQ-036 (BOLA/BFLA Applicability)**: This ticket introduces no application authorization surface (no GraphQL resolvers, no DB access under authenticated user context). IF later tickets wire additional CI jobs touching application services THEN those additions SHALL re-evaluate BOLA/BFLA per their own specs; DEV3-001 records N/A explicitly to keep the audit trail honest.
- **REQ-037 (Rate/Abuse Bounding)**: WHEN evaluating cost/abuse THEN the workflow SHALL rely on per-PR concurrency cancellation (REQ-024) and default GitHub token rate limits; no public self-hosted execution is introduced. IF the repository later becomes public THEN a follow-up must restrict PR-triggered job minutes (recorded here as a forward-guard).
- **REQ-038 (Log Sanitization)**: IF test or lint output could contain environment-derived values THEN CI runs SHALL use the test-time logger posture (`TEST_SERVER=1` / `TEST_CI=1` where applicable) so expected-rejection logs collapse to debug, and no raw `.env` content is ever printed. Secret masking beyond GitHub's built-in masking SHALL NOT be relied upon (secrets stay out of logs by construction).
- **REQ-039 (Artifact Policy)**: IF run artifacts (logs, baselines) are uploaded THEN they SHALL exclude environment files, caches, and `.git` contents, and SHALL have a short retention (≤ 7 days). Default: no artifacts uploaded unless debugging requires it.

### 2.4 Atomicity, Concurrency & Data Integrity (REQ-040..REQ-047)

- **REQ-040 (Ephemeral Database per Job)**: WHEN DB-backed tests run THEN each job SHALL receive its own provisioned PostgreSQL service and SHALL bootstrap schema fresh into the ephemeral instance. IF two jobs run concurrently THEN they SHALL share no database state (fully isolated services — no shared "CI database").
- **REQ-041 (Idempotent Re-Runs)**: WHEN a pipeline run is retried (Re-run failed jobs / Re-run all) THEN every stage SHALL behave identically against the same commit — no step may depend on mutable external state other than package registries and action downloads. IF a step is not deterministic THEN it must be redesigned or deferred (logged in `deferred-items.md`).
- **REQ-042 (No In-Band Schema Mutation of Persistent Infra)**: The pipeline SHALL only ever `db push` into its ephemeral service container. Under no circumstances SHALL CI target a shared/dev/production database connection string (enforced by construction: no such secret is in scope — see REQ-031).
- **REQ-043 (Transactional Test Isolation Enforced by Suites)**: WHEN CI executes `test:db` THEN the suites' `runInRollback` + `tx`-propagation discipline (per `backend/db/test/AGENTS.md`) is the data-integrity mechanism; CI SHALL apply no additional database teardown assumptions beyond the ephemeral container lifecycle.
- **REQ-044 (Concurrency Group Correctness Across Event Types)**: WHEN concurrency is configured THEN PR-event groups SHALL be keyed by PR number (safe cancel), and push-event groups on `develop`/`main` SHALL be keyed per-ref without in-progress cancellation (REQ-024), so branch-health signals are never discarded by racing merges.
- **REQ-045 (Cache Atomicity)**: WHEN caches are saved THEN save keys SHALL be content-addressed enough (lockfile hash) to avoid restoring semantically mismatched caches; a poisoned or partial cache restore SHALL degrade to a correct-but-slower run, never an incorrect pass.
- **REQ-046 (Check Aggregator Atomicity)**: IF a final aggregate job (e.g., `ci-verdict`) is used to simplify branch protection THEN it SHALL evaluate only after all constituent jobs complete, SHALL fail if any constituent failed or was cancelled, and SHALL itself be the single required check — otherwise (preferred default) each named check is individually required (REQ-018) and no aggregator exists.
- **REQ-047 (Fork/Concurrency Interaction)**: WHEN a fork PR and a same-branch rapid push sequence interleave THEN each concurrency group SHALL independently cancel only its own superseded runs; no cross-group cancellation may occur.

### 2.5 Validation & Error Contracts (REQ-050..REQ-057)

- **REQ-050 (Blocking Failure Taxonomy)**: WHEN any of the following fails THEN the corresponding named check SHALL report failure and block merge: type errors (`tsgo`), oxlint violations, biome issues, ESLint errors, duplication threshold breaches, DBML validation errors, Mermaid validation errors, and any test failure in the PR-scoped suites. Warnings-only tool exits that do not fail the tool's own configured exit contract SHALL NOT block (the repo's configs already deny-warnings where that posture is intended).
- **REQ-051 (Exit-Code Contract)**: WHEN a pipeline step executes a project command THEN the step SHALL propagate the command's exit code directly (no `|| true` / no `continue-on-error: true` on required checks). IF a diagnostic/informational step is allowed to fail THEN it SHALL be visually distinct from required checks and documented in the workflow header comment.
- **REQ-052 (Missing Tooling Contract)**: IF `bun validate:dbml` or `scripts/validate-mermaid.ts` does not exist or exits as "command not found" at implementation time THEN implementation SHALL create the missing wiring as part of this ticket (the scripts already exist per `docs/README.md` validation table; CI must invoke them, and any packaging gaps discovered become in-scope fixes).
- **REQ-053 (Error Message Attribution)**: WHEN a check fails THEN the job log SHALL make the failing domain self-evident from the step name (e.g., `DBML validation (db/schema.dbml)`, `Mermaid validation (changed docs)`, `ESLint (full-repo)`, `DB tests (runInRollback suites)`) — operators must not need to open the raw log to know which validator failed.
- **REQ-054 (DomainError/i18n Error Contracts — N/A)**: This ticket adds no application resolvers/services; DomainError subclasses and `extensions.code` mappings are NOT applicable. IF any new script throws user/operator-facing errors THEN it SHALL use localized messages via `getServerTranslations` (REQ-002) and non-zero exit codes — never bare `console.error` + ambiguous exits.
- **REQ-055 (Timeout Distinctness)**: WHEN a job is killed by `timeout-minutes` THEN the resulting failure signal SHALL be unambiguous (GitHub's timeout annotation) and counted as a blocking failure of that check.
- **REQ-056 (Flake Handling Contract)**: IF a test suite flakes in CI THEN the remediation path SHALL be fixing the flake — not retries with eventual-pass tolerance. The workflow MAY rely on GitHub's manual re-run for transient infra failures (registry outage), but SHALL NOT include automatic `retry-on-failure` logic for test steps.
- **REQ-057 (Green-Signal Semantics)**: WHEN the `tests` check passes THEN it SHALL mean: all PR-scoped suites ran to completion and passed on the PR's merge-target state. Partial-suite greens (skipped files due to environment gating) SHALL be visible in the job summary so a "green" is not silently a smaller suite.

### 2.6 GraphQL & Frontend Contracts (REQ-060..REQ-063)

- **REQ-060 (No Schema Surface Introduced)**: This ticket SHALL NOT modify GraphQL types, resolvers, Pothos files, frontend documents, or views; therefore no Pothos mutation/query signatures, no `TypedDocumentNode` additions, and no MUI v9 changes are introduced. This N/A affirmation is itself a requirement so reviewers know the absence is intentional.
- **REQ-061 (Schema/Codegen Drift Gate — Conditional Inclusion)**: IF implementation evidence shows `bun run generate:gqlSchema` + `bun codegen` is reliably reproducible in CI within time budgets THEN the quality job SHOULD add a drift check: run codegen and fail on a non-empty `git diff` of generated artifacts. IF it proves flaky in CI THEN it SHALL be recorded as a deferred item (with owner) rather than shipped as a flaky required check.
- **REQ-062 (Frontend-Impacting Changes Still Gated)**: WHEN future PRs modify frontend code THEN the existing quality + component-test checks introduced by this pipeline SHALL apply to them unchanged — no additional wiring per-feature is expected.
- **REQ-063 (Documentation File Watch Set for Mermaid Gate)**: WHEN the docs-validation job computes its file set THEN the watch patterns SHALL include `docs/**/*.md`, all `*.mmd` files, and any other committed markdown known to embed Mermaid blocks (verified by grepping for ```` ```mermaid ```` fences during implementation and recording the final pattern list in the workflow comment).

### 2.7 Test Coverage & Verification of the Pipeline Itself (REQ-070..REQ-077)

- **REQ-070 (Positive-Path Evidence)**: WHEN this ticket completes THEN the plan outcome SHALL contain links/exports of at least one green CI run on the ticket's own PR proving every named check passes.
- **REQ-071 (Sabotage Verification — DBML)**: WHEN verifying the pipeline THEN an intentionally-broken `db/schema.dbml` (invalid syntax or invalid block) SHALL be demonstrated to fail the `dbml-validation` check and block merge (via a throwaway commit on the feature branch, reverted before merge).
- **REQ-072 (Sabotage Verification — Mermaid)**: A documentation file containing an invalid `mermaid` block SHALL be demonstrated to fail `docs-validation` when the file is in the changed set, and to be correctly skipped (passing no-op) when documentation is untouched (REQ-017).
- **REQ-073 (Sabotage Verification — Quality Gate)**: A deliberate lint/type violation SHALL be demonstrated to fail the `quality` check with the violating file/rule visible in the log (REQ-026 attribution).
- **REQ-074 (Sabotage Verification — Test Stage)**: A deliberately failing test SHALL be demonstrated to fail the `tests` check, and its restoration SHALL return the check to green on re-run (proving REQ-041 idempotence).
- **REQ-075 (Changed-File Detection Unit Verification)**: WHEN the changed-file composition script (REQ-027) is implemented THEN it SHALL have unit coverage (bun:test, no DB — plain script test under the scripts test conventions) for: no-changes, docs-only-changes, code-only-changes, mixed-changes, and deleted-file edge cases. Edge/boundary cases (empty diff, binary files) SHALL be covered per the 4-tier discipline's Tier 1/Tier 2 scope for scripts.
- **REQ-076 (No `runInRollback` Applicability Statement)**: This ticket adds no repository-layer code; the 100%-coverage `runInRollback` discipline is NOT applicable to its own artifacts, but the CI it ships is exactly what enforces that discipline for all future tickets — the traceability matrix records this relationship explicitly.
- **REQ-077 (Concurrency/Cancellation Verification)**: WHEN verifying REQ-024 THEN two rapid successive pushes on the PR SHALL be shown to leave only the latest run executing (earlier run cancelled), and a branch-push run on `develop` SHALL be shown to NOT be cancelled by a subsequent independent commit context per design.

Layer AGENTS.md updates SHALL be limited to rules-only one-liners if any (expected: none beyond root — workflow files live under `.github/`); `.agents/skills/quality-gate`/`quality-loop` SHALL NOT be semantically altered by this ticket (local loops remain authoritative for per-file work).

## 3. System Decisions & State Machine Invariants Alignment

- **Decision References (docs/specs/open-decisions-and-gaps.md — 33 resolved A.1–C.5)**:
  - DEV3-001 does not implement domain behavior and therefore **claims no primary ownership** of any A/B/C decision. Its alignment role is *enforcement-by-gating*:
    - **Whole catalog (A.1–C.5, schema ground truth)**: Decision B.4 escrow, B.12 single-parent link, C.5 recitation 1:1, etc. are encoded in `db/schema.dbml` and the Drizzle schema; REQ-016 makes `bun validate:dbml` an always-on merge gate so the structural ground truth of all 33 decisions can never drift unvalidated into `develop`.
    - **Documentation-bound invariants**: The workflows embodying the resolved decisions (e.g., B.15 inactivity, B.16 request preference — `docs/workflows/02-on-demand-matching-workflow.md`) contain 20 validated Mermaid blocks; REQ-017 guarantees documentation edits (including any future edits to those workflow docs) are Mermaid-valid at merge time (`docs/README.md` validation table is the precedent this ticket operationalizes).
- **State Machine & Lifecycle Invariants (docs/specs/state-machine-invariants.md)**:
  - **INV-S1..S8 (Session), INV-TV1..TV7 (Teacher Verification), INV-B1..B6 (Balances), INV-W1..W8 (Wallet), INV-U1..U5 (Governance), INV-P1..P4, INV-PAY1..PAY5, INV-HW1..HW4, INV-PR1..PR3, INV-E1..E6**: These are verified by automated tests delivered in later tickets (notably DEV2-022 invariant verification, plus each feature ticket's suites). No invariant is weakened, re-interpreted, or re-scoped by this ticket.
  - **No new invariants introduced**: The pipeline itself is stateless infrastructure; it adds no entities, no state machines, and no lifecycle transitions to the domain model.
